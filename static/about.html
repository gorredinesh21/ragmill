How RAGMill is built

One FastAPI service, one vector store, one embedding model that runs in-process — and a query pipeline small enough to hold in your head.

The pipeline, in plain language

1
Chunk

Each document becomes a chunk (title + abstract — one chunk per paper here, but IDs carry a chunk index so full-text PDFs slot in later). Stubs and duplicates are dropped before anything expensive happens.

2
Embed

fastembed runs the bge-small-en-v1.5 ONNX model inside the process — 384-dim vectors, no embedding API, no quotas to hit.

3
Hybrid search

Two engines run on every query: dense vector search (Qdrant, cosine) for meaning, BM25 keyword search for exact terms. Each returns its own ranking of the same corpus.

4
Fuse with RRF

Reciprocal Rank Fusion merges the two rankings: score(d) = Σ 1/(60 + rank). Simple, parameter-light, and — measured — better than either engine alone. This is the number the Eval page is about.

5
Rerank

Gemini re-orders the top candidates listwise in a single call. No credentials? A clearly-labeled lexical fallback runs instead — nothing pretends to be a model it isn't.

6
Cited answer

Gemini writes a short answer grounded in the top passages with [n] citations, streamed to your browser over SSE in three stages (retrieve → rerank → answer) so you see the evidence before the conclusion. Try it on the Ask page.

The million-document plan

Sharded, restartable ingest

Ingestion runs as a Cloud Run Job — 10 parallel tasks, each embedding its slice of the corpus and upserting to Qdrant. Every point ID is a deterministic uuid5 of the document ID + chunk, so upserts are idempotent: kill the job mid-run, re-execute, and the count never double-counts (that property is unit-tested). Each task writes progress to a status object so a 1M run is observable.

What the arithmetic says

Measured single-node throughput under heavy load was 4.7 docs/s; the conservative cloud estimate is 150–250 docs/s per shard — so 10 shards ingest 1M documents in roughly 7–12 minutes of job time. That full benchmark run is planned, not yet executed; the 5K-scale numbers on the Eval page are measured, and the honest status table lives in the README.

Cost

Demo serving

Cloud Run, scale-to-zero, cold-booting from a bundled 23 MB index snapshot in seconds: < $1/month idle.

Embeddings

In-process ONNX — $0, and there is no API quota to hit at 1M-document scale.

Full 1M ingest run

10 tasks × ~10 min of 1-vCPU time: < $1 per run, and re-runs are no-op upserts.

Honest limits (read this part)

This public demo runs on a synthetic corpus — 5,000 deterministic, arXiv-style papers generated by a seeded script, not real arXiv metadata. The retrieval metrics on the Eval page are real measurements over that synthetic golden set, and the real-arXiv loader (scripts/fetch_arxiv.py) exists for the genuine 1M run. Without an LLM key configured, answers come from a clearly-labeled extractive mock (you can see which backend answered in the answer header on the Ask page). The 1M benchmark is a runnable plan, not a completed run — nothing on this site claims otherwise.
